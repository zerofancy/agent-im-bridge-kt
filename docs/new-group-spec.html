/new group [群名]

2026-10-27 · 第二版：参数由“初始问题”调整为“群名”。本次修改未部署，不代表线上行为已切换。

核心契约：机器人创建仅含本人和当前机器人的私有普通群，继承来源聊天工作目录，绑定独立 Agent 会话。参数仅用于群名，不提交模型；用户可先在新群 /cd 再发问题。原聊天会话不变。

1. 命令

输入行为
/new group 登录问题排查群名为“登录问题排查”；创建并绑定会话，不执行登录排查任务。
/new group群名使用“Agent 会话 · MM-dd HH:mm”；不运行模型。
/new 修复登录问题保留原行为：当前聊天新建会话并执行初始输入。
/new -- group 修复登录问题普通 /new，初始输入以 group 开头，不建群。
  • 仅完整小写 group 子命令触发建群，grouping 不匹配。正文内部空格保留，不进行 shell 解释。
  • 群名最多 60 个 Unicode codepoints；拒绝控制字符、换行及 Unicode 行/段分隔符，不静默截断。省略或仅空白时使用默认名。
  • 仅飞书授权用户可用；群内仍须明确 @机器人。文档评论、表情、桌面、Telegram 不支持，不降级为普通 /new。
  • 只接受文本参数，不迁移附件、回复链、旧模型上下文或工具结果，不额外邀请其他用户。

2. 使用流程

来源聊天：/new group 登录问题排查
来源聊天：正在创建新群会话…
新群：新群会话已就绪。工作目录：<继承目录>
      尚未提交模型任务，可先 /cd，再 @机器人发送问题。
来源聊天：群跳转链接、继承目录、新 Session ID
新群用户：@机器人 /cd /absolute/target
新群用户：@机器人 请检查登录问题
  • 群名不是用户问题，不发送“初始问题”转述，不触发仅基础提示的空轮次。
  • 来源聊天仍保持原会话及目录。后续进度、答案和图片按实际新群消息路由，不同步复制到来源。
  • 新群后续首次实际模型输入沿用基础提示与用户要求分隔机制；/cd、/pwd 等控制命令不触发模型。
  • 创建期间提前收到的新群消息等待初始化结束；这些是用户独立发送的消息，初始化后正常 FIFO，不是把群名转成任务。

3. 隔离、鉴权与目录

  • 来源聊天需空闲、无队列、无接收准备和切换屏障；排空或关闭时不接受新建群。建群准备不占模型并发槽。
  • 规范化来源实际选择目录并冻结快照，不使用 Bridge/JVM cwd 推断业务目录。
  • 新群先持久化目录，再创建并绑定本实例后端的新原生会话；SessionKey 使用当前 appId、新 chatId、workspace、runtimeRoot、backendId。
  • 继承当前后端和 sandbox 配置，不复制其他环境凭据。DEV/PROD、不同机器人及后端状态隔离。
  • 两个聊天共享同一文件目录，不提供自动 worktree 或文件写互斥。双方后续 /cd 互不影响。
  • 用户为本实例 allowedUserId，机器人使用本实例身份；群主为该用户。其他群成员即便入群也不能调用机器人。
  • 建群前检查后端支持会话创建，成员核查通过前不向新群披露目录或启动业务。机器人就绪消息事件不会作为用户消息执行。

4. 协调与接口

  • 使用 官方创建群接口，机器人 tenant token、open_id、private 普通群，指定 allowedUserId 为群主和用户成员。
  • 分页核查用户成员；通过 members/is_in_chat 核查当前机器人在群。
  • 新增出站使用自建 HTTP JSON 封装及 SDK 公开 token manager；关闭写请求隐式重试和重定向，不调用 lark-cli、不借用户 token。
  • 建群、就绪消息分别使用稳定 uuid。本地操作 ID 包含实例/应用/后端/来源聊天/命令消息身份，外部写前登记。
  • 所有业务锁只管理状态和调度，不在业务 Mutex 内执行网络或文件 I/O；存储自身通过 Mutex 和 NonCancellable 原子提交。
  • 主要组件为 GroupConversationService、GroupConversationGateway、GroupCreationStore、ChatService、SessionStore。

5. 状态与异常

RESERVED → CREATING → GROUP_CREATED → MEMBERS_VERIFIED
→ SESSION_BOUND → READY
分支：FAILED / UNKNOWN / CANCELLED / RECOVERED
  • READY 代表目录与独立会话绑定、就绪消息交付及初始化交接完成，不表示任何模型任务已经执行。
  • 相同命令事件只关联同一操作，不重复创建群。用户新发另一条命令是新操作。
  • 结果不明时保留操作编号和已知群链接，不盲目重发建群或就绪消息，不自动解散残留群。
  • 停止在建群写请求已提交后只记录意图，在 30 秒技术超时内收取并保存返回的 chatId，再停止后续步骤；读取与后端准备可取消。
  • 来源或初始化中的目标群 /stop 可取消创建后续步骤，旧挂起命令不会越过停止水位。交接后来源 /stop 不影响新群独立任务。
  • 来源确认发送失败不回滚 READY；旧流程 finally 不清理目标群后续 /cd、/new 等新操作的屏障或句柄。

6. Review 修复：缩小恢复保护范围

  • 不再使用“存在任何 UNKNOWN/CREATING 无目标 ID 记录”作为全群门禁。遗留无目标 ID 操作不拦截其他聊天。
  • 启动时从持久化 SessionStore 恢复当前 app/runtime/backend 的已登记聊天；已有 workspace 或 session 的老群不作为未知候选群。
  • 保护仅覆盖明确失败的目标群，以及创建窗口中实际收到消息、尚未登记且无法排除关联的候选群。候选 chatId 单独持久化，不扩大为全体群。
  • 候选等待请求在结果不明时取消，不把其队列释放到默认目录运行。其他无关群仍正常运行、切目录和停止。
  • 受保护群 /pwd 说明预期目录；必须 /cd 绝对路径恢复，不按默认目录解析相对路径。/stop 始终可用。
  • 无法确认但也从未观察到的目标群，不凭群名或任意未知 chatId 猜测归属；操作停在 UNKNOWN，需用户核实实际群和目录。

7. Review 修复：恢复半成功明确反馈

  • /cd 先完成 SessionStore 的原子目录提交；GroupCreationStore 的恢复记录、确认集合和候选隔离集合在另一次单事务中一起提交，不逐条半更新。
  • 若恢复事务失败，回复明确包含“当前目录已保存：目标路径”“恢复状态保存失败”“群仍暂停执行”“目录未回滚”，不得仅记录日志。
  • 恢复失败时不清内存保护；修复存储后重试 /cd 绝对路径。只有恢复落盘成功，才同步解除内存保护。
  • 两个存储之间不声称分布式事务；保留安全的半成功状态，并让用户可观察、可重试，不回滚已成功目录。

8. 兼容与重启

建群前实时查询 application/v6/scopes，仅接受 tenant 身份且已授权的权限。缺少创建群、读取成员或机器人发消息能力时，不创建群、不登记创建操作，直接发送最小缺失权限的申请链接。用户或管理员确认申请、审批并发布生效后，需显式重试命令；不以用户 OAuth 替代应用授权，也不自动批量申请其他权限。查询失败时停止建群。若权限在创建后变化，明确提示群已创建但初始化未完成，并保留群链接。

  • 旧版本 QUEUED 记录保留兼容：结合 SessionInitialization 判断未提交或结果不明，首次连接后最多尝试一次恢复提示，不自动重跑。
  • 新版本 READY 不产生首问任务，也不触发旧首问恢复提示；会话 PENDING 状态等待用户第一条实际问题。
  • 内存队列不持久化或自动恢复。状态文件不可读时明确失败，不覆盖损坏文件，不跨环境借状态。

9. 验证与非目标

  • 覆盖群名原样传递、60 Unicode 边界、控制字符拒绝、默认名、普通 /new 和 -- 转义。
  • 覆盖建群不调用模型、PENDING 绑定、先 /cd 再首问、来源不变、目录继承、幂等、停止和初始化 FIFO。
  • 覆盖 UNKNOWN 残留下老群及无关群不误拦、创建窗口老群可执行、候选保护按 chatId 持久化。
  • 注入 group 恢复写失败，验证目录已提交、明确反馈、仍暂停、无部分确认状态及修复后可恢复。
  • 验证行数、diff、单测与 installDist；真实 DEV 群主/权限/入群/目录/问答效果仍需在线验收。
  • 不自动提权、改机器人权限、部署、提交、推送、建 worktree、迁移历史或邀请任意成员。
