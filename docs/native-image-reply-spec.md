# 后端原生图片结果转发 Spec

状态：待实施。日期：2026-10-17。

## 目标与范围

Bridge 解析 Codex 和 OpenCode 已有的结构化结果，将可确认是输出产物的图片转发到当前 Telegram 会话。图片回复复用当前请求的身份校验、路由、队列和生命周期；模型无需知道机器人凭据、聊天 ID 或 Bridge 项目实现。

不修改 OpenCode 或 Codex 内部，不注入特殊提示词，不新增 MCP 或其他模型工具。此次交付为设计文档；业务实现、提交及部署另行进行。

首期完成两个后端的结果解析、统一附件模型与 Telegram 图片发送。飞书、桌面及文档评论保持现有文本能力，对未支持的图片输出给出明确提示，不静默丢弃。图片输入、任意文件发送、从 Markdown 图片链接或正文路径提取附件、扫描工作目录发现图片均不在范围内。

## 现状与协议依据

`AgentResult.Success` 当前只有文本及会话 ID。`AppServerAgentRunner` 只从当前轮完成的 `agentMessage` 提取文本；`OpenCodeRunner.openCodeText` 只提取文本 part。纯图片结果会被当作空答案，工具图片也没有进入出站发送流程。

Codex 本机导出的协议包含 `imageGeneration`，其字段包含 `id`、`status`、`result`、`failure` 及可选 `savedPath`。字段存在不意味着每个通知都包含图片字节；解析必须兼容仅有路径的结果，并以实际安装版本的完成事件建立测试样本。

OpenCode 1.16.0 的 `FilePart` 包含 `mime`、`url` 和可选 `filename`；完成工具的 `state.attachments` 可包含这些文件。内置 `read` 同样会返回图片附件，因此“存在图片附件”不构成对用户交付的充分依据。

协议参考：

- [OpenCode 1.16.0 类型定义](https://github.com/anomalyco/opencode/blob/v1.16.0/packages/sdk/js/src/v2/gen/types.gen.ts)
- [OpenCode 1.16.0 read 实现](https://github.com/anomalyco/opencode/blob/v1.16.0/packages/opencode/src/tool/read.ts)
- Codex：使用本机 `codex app-server generate-ts` 的 `ImageGenerationItem.ts` 和 `v2/ThreadItem.ts`；实施时记录 CLI 版本及脱敏事件 fixture。

## 图片选择规则

### Codex

只收集当前请求对应 thread、turn 内的 `imageGeneration` 完成结果；整个 turn 成功结束后才允许交付。失败、仍在进行、没有可用内容的生成项不发送。

优先使用有效的 `savedPath`；路径不可用时尝试事件中有效的内嵌图片 `result`。不得假定 `result` 一定是 URL 或无条件 Base64 解码，须按已验证的版本格式解析。两种来源均不可用时记录交付问题，保留文字答案。

`imageView`、普通工具返回的图片以及用户输入图片不转发。最终文字继续只从本轮完成的 `agentMessage` 提取，沿用现有 phase 选择规则。

### OpenCode

在当前 session、当前请求 parentID 对应的 assistant 消息集合中，收集状态为 completed 的工具附件；覆盖当前请求的中间工具消息，而不只检查最终文本所在消息。以该请求成功完成作为统一发送门槛。

采用 Bridge 本地的“已知图片产物工具”适配表：按完整工具标识精确匹配，并固定其附件位置与支持的 URL 编码。只有经过协议样本确认、用途为生成或导出图片的工具进入适配表。不以名字包含 image、generate 等关键词猜测用途，也不从自然语言判断发送意图。

适配表是 Bridge 的解析配置，不向模型暴露新工具，不要求上游输出新增 metadata。每个条目必须有成功、失败、观察图片混入的回归样本。内置 `read` 等观察工具禁止加入；未知工具附件、无法归属已知产物的顶层 `file` part 默认不发送。

目前尚未确认本机 OpenCode 已有哪一个图片生成工具及其实际返回样本，初始适配表为空。首期可以完成附件解析与过滤框架，但在验证并接入至少一个已有生成工具前，不宣称 OpenCode 图片生成转发已可用。不得为填补此缺口新增工具或提示词。

这项取舍会漏掉语义不明确的图片，但避免把模型查看的截图、输入图或工作文件自动发送出去。只在协议给出附件而缺少已知产物归属时提示“本轮存在图片附件，但无法确认其为输出产物，未自动发送”；已知观察工具的图片不产生提示。

## 统一结果与附件准备

扩展 `AgentResult.Success`，保留现有 `text`、`sessionId`，增加默认空列表的 `images` 和 `deliveryIssues`。图片描述至少包括后端、请求标识、来源 item 或 part ID、附件序号、内容来源与声明 MIME。问题使用枚举分类，不携带完整协议正文。

后端适配器只产生候选描述；公共附件准备组件负责校验、受限解码和临时存储。有效文本或至少一张有效图片即可构成成功结果；全部缺失时沿用 EMPTY。存在图片候选但全部无效时，应给出“图片结果无法读取或发送”的明确说明，不能冒充成功交付。

首期产品限制为每轮最多 10 张、每张源文件不超过 10 MiB、合计不超过 30 MiB。限制适用于读取及解码过程，而不是完整分配内存之后。超出的图片不发送并提示数量；实施时同时核对 Telegram 的实际限制，以更严格者为准。

只接受经文件签名及图片解码验证的 PNG、JPEG、静态 WebP；限制解码像素数为 4000 万，防止小文件导致过量内存占用。MIME 与实际格式冲突、损坏图片、动画或其他格式均按不支持处理。WebP 如需转换，使用受限的图片解码流程转为 PNG。

支持内嵌数据和已知后端明确输出的本地文件路径。首期不抓取 HTTP(S) 图片地址，不将任意 URL 交给 Telegram 下载。未知 scheme、无效 Base64 和不存在文件均成为单张附件的问题，不导致重跑模型。

本地路径解析须明确基准目录；相对路径仅在后端协议给出基准时接受。规范化并解析符号链接后，路径只能位于当前聊天工作目录或当前环境后端明确使用的图片产物目录。其他位置不读取，不扩大到整个用户主目录。读取时执行类型、大小及文件一致性检查，复制到当前环境的附件临时区，后续仅上传该副本。不能只校验路径字符串后重新无条件打开源路径。

附件临时文件归当前请求所有，不改写原文件，不持久化进会话绑定。请求完成、失败、取消时清理；启动时清理同环境遗留且不属于活动请求的暂存文件。dev 与 prod 使用独立目录。

## Telegram 交付流程

统一交付流程为：确认后端成功结束 → 准备图片 → 发送最终文字 → 按顺序上传图片 → 汇总交付结果。图片不在进度事件中提前发送，不因卡片多次刷新重复发送。

新增通道媒体发送能力，由 `ChatService` 使用原 `ReplyRoute` 调用；TelegramClient 封装 multipart 图片上传。机器人 token 仅留在通道客户端。所有文字及失败说明继续走统一文字发送入口。

首期逐张发送图片，不使用相册。每张都保留原消息回复关系和现有话题路由；不得从模型结果读取目标 chatId。文字与图片分开发送，不把整个答案塞入 caption。纯图片结果跳过空正文发送，已有进度消息显示图片交付状态。

通道不支持图片时保留文字，并给出“当前通道暂不支持发送图片，共 N 张未发送”；不输出服务器本地路径充当可下载链接。

按本轮首次出现的产物顺序发送。同一 item 或 part 的重复通知按来源 ID 与附件序号归并；不同 item 内容相同的图片在准备后按摘要去重，仅限当前请求。不得按会话级摘要去重而阻止用户再次索取同一图片。

文字发送状态与图片发送状态分开记录。只有文字和所有选中图片均确认交付后才显示“已完成”；有部分图片失败显示“部分图片未发送”。已有文字不重发，成功图片不重发，模型不自动重跑。

确定未发送的单张失败可以继续后续图片并汇总数量；请求可能已被 Telegram 接受而响应丢失时标记“交付未确认”，不自动重试该张。首期不做跨进程恢复重发，不承诺外部 API 的 exactly-once。发送使用现有技术超时；不得新增模型运行超时。

## 调度与异常

同聊天槽位持续占用到文字、图片发送及清理结束，后续请求不能穿插图片。不同聊天维持既有并发上限，附件 I/O 不在调度 Mutex 内执行。

每次上传前检查停止意图。等待发送时 `/stop` 可以取消等待并停止后续上传；已经提交给 Telegram 的请求无法保证撤回，不能把它记为确定未送达。后端已结束时不要为了中止附件发送再次启动或重跑模型。

失败或中断的模型轮次不交付其缓存图片。Bridge 关闭时停止后续上传，清理在所属生命周期内完成。阻塞读写放在 Dispatchers.IO，取消异常必须传播，NonCancellable 只用于必要清理。

附件校验失败与已分类的网络失败为可恢复交付问题；内部编程错误沿用 FatalErrorHandler，不以宽泛 catch 吞掉。日志仅记录请求关联 ID、来源类型、数量、字节数、状态及脱敏错误分类；不记录图片字节、data URL、带凭据 URL、正文和完整协议载荷。

## 实施位置

| 位置 | 改动 |
| --- | --- |
| AgentRunner.kt | 附件结果与交付问题模型；兼容纯文本后端 |
| backend/AppServerAgentRunner.kt | 当前轮图片完成项收集及终态筛选 |
| backend/OpenCodeRunner.kt | 当前请求工具附件收集、已知工具适配与筛选 |
| 公共附件准备组件 | 文件校验、受限读取解码、去重、暂存与清理 |
| ChatService.kt | 统一交付编排、纯图片成功、取消与部分失败状态 |

| StreamingReply 及 TelegramCardReplies | 文字完成与整体媒体交付完成分离 |

实施顺序：先添加脱敏协议样本和统一结果类型，再接 Codex 与 Telegram 的端到端发送，最后依据实际已有工具样本接 OpenCode 适配条目。没有合格 OpenCode 样本时保留明确的不支持状态，不用猜测规则替代。

## 验收

1. 文字回复及纯文本后端行为不变；成功的纯图片结果不报 EMPTY，图文结果均可交付。
2. Codex 成功图片分别覆盖路径、内嵌内容、空结果、失败项和重复完成事件；imageView 与其他轮次图片不发送。
3. OpenCode 覆盖中间 assistant 工具消息、已有生成工具附件、read 图片、未知工具、历史请求和未完成工具；仅合格产物可发送。
4. 验证 MIME 伪装、损坏图片、超大文件、超量、路径越界、符号链接变化、远程 URL 和临时文件清理。
5. Telegram 使用 fake API 验证 multipart、原消息路由、纯图片、逐张次序、部分失败和响应丢失；没有重复文本或自动重跑。
6. 验证同聊天串行、跨聊天并发与上限、失败后出队、等待上传时取消、停止后新请求等待清理、关闭后不继续发送，以及后端进程清理不受影响。
7. 行为实现完成后运行 `./gradlew test installDist`；真实图片测试仅在 dev 使用测试素材进行，通过 bridgectl 部署。此次文档编写不启动模型、不发送消息、不部署。
