飞书表情消息与表情回复接入调研

2026-09-10 · agent-im-bridge-kt · 只调研，未修改业务代码

结论与范围

两项需求都可实现：普通消息中的内置表情统一转换为方括号文本；用户对本机器人消息新增的表情回复，转换为带原消息上下文的新用户请求，进入现有模型队列。无需先做卡片，也无需改变 Codex / Traex 协议。

独立 sticker 表情包需要区分：协议可能仅提供 file_key，没有语义名称，不能保证转换为 [YES]。首版明确支持有文本或 emoji_type 的内置表情；未知贴纸保留“无法识别的表情包”，不猜测确认或否定。

1. 普通消息中的表情

输入类型当前行为建议
text 中的 [Yes]、[OK] 等extractPrompt 读取原始 text，已保留文字与空白。保留正文，只对已知表情文本别名做规范化；不对任意方括号内容进行替换。
post 中的内置表情项目保留原始富文本 JSON，只替换图片资源。emotion 节点未变成用户期待的表情文本。按结构将 emotion 节点变成 text 节点，保持顺序、行结构及其他富文本字段。
Unicode 表情，如 👍作为正文文字保留。默认原样保留，不擅自将每个 Unicode 表情解读为批准。
sticker当前入口拒绝；引用历史显示不支持。SDK 也只提取 file_key。无法仅凭 key 判断含义。不要创建未经验证的 key 到 Yes/No 映射。

官方富文本表情标签是 emotion，不是 emoji：

{"tag":"emotion","emoji_type":"Yes"}
→ {"tag":"text","text":"[YES]"}

依据：发送消息内容结构（已读取官方 Markdown 正文）。客户端实际接收形态需用脱敏事件 fixture 补充验证。

官方标识建议展示
Yes[YES]
No[NO]
OK[OK]
FISTBUMP[碰拳]
其他可识别标识有明确别名则用别名，否则 [原始标识]

协议标识保留原大小写，展示名称单独映射；不要把 API 的 Yes 改为 YES。标识列表依据：官方表情文案说明。

当前消息及 ReplyContext 中的历史消息共用相同转换器。只转换结构化表情节点及明确的文本别名，不改代码块、链接、资源 key，也不同时拼接 content 与 content_v2 造成重复。表情混合消息仍走模型，不能被误识别成即时斜杠命令。

2. 表情回复是一种独立输入事件

订阅 im.message.reaction.created_v1（控制台名称“消息被reaction”），无需轮询。当前 SDK dispatcher 已注册底层处理器，Bridge 增加 channel.on<ReactionEvent>("reaction") 即可进入适配层，但控制台订阅仍必须配置。

事件包含 message_id、reaction_type.emoji_type、operator_type、user_id.open_id、action_time，以及事件头 event_id。它不提供 chat_id 和被回复正文，因此需从本机器人出站消息记录或消息查询中获取关联信息。复用现有长连接；官方事件页提供 Java WebSocket 示例。

订阅权限为 im:message.reactions:read 或 im:message:readonly 任一项；原消息查询权限另按现有获取消息能力核对。无需为了识别当前用户申请 employee user ID，使用 open_id 即可。依据：新增消息表情回复。

SDK 2.7.3 的 ReactionEvent 注释写 created/deleted，但实际 ChannelInboundProcessor 传入的是 added/removed。应按源码中的 added 处理新增，不能照注释判断而导致收不到请求。

要按这个方案继续吗？

【用户通过表情回复发送的新消息】
[YES]

上述是输入结构示意。实际仍附用户身份、操作时间和原消息标识，将引用正文明确隔离为历史内容。模型据此理解确认对象；桥接层不把 Yes 硬编码成自动执行，也不把 No 硬编码为 /stop。

3. 当前项目需要处理的关键点

  1. 权限过滤必须独立完成。SDK reaction 使用 pushLight，仅去重后分发，不经过普通消息的 allowlist / mention 检查。校验 operator_type=user 和原始 open_id=allowedUserId；排除所有应用操作，尤其是本机器人自动添加和移除的 Typing，避免循环触发。
  2. 只接受对本机器人的回复。核对目标消息属于本应用机器人且聊天一致，不能只判断 sender_type=app。普通群消息仍要求 @机器人；针对本机器人消息的表情回复作为本次新增的明确指向机器人入口，无须虚构 @ 标签。其他用户和其他机器人的消息均不触发。
  3. 分离请求身份、引用目标与回复路由。现有 AgentRunHandle 使用 route.messageId，ReplyContext 又把该 ID 作为历史 visited 起点。若 reaction 的 route.messageId 和 parentId 都填原机器人消息 ID，会直接触发循环检测。新增独立 inputId / eventId；引用目标及飞书 replyTo 保留真实 om_ 消息 ID。合成 rx: 标识只在内部使用，不能传给飞书消息接口。
  4. 出站记录与历史 LRU 不同。现有 SentMessageLru 是模型已看到的消息集合，不是可靠的机器人出站消息索引。建议记录实际发出的 messageId → chatId / appId / session 绑定，覆盖长答案分片。缓存缺失时可查消息核验身份；原文或身份无法确认时，不把裸 [YES] 交给模型。
  5. 保持 FIFO。表情输入先进入统一接收与排队流程，在请求准备阶段读取引用正文，不能先异步查询完才随意插队。缓存缺失、chatId 尚未知的事件需要在统一入站排序层保留接收序号，与普通消息合并处理；即时 /stop 等命令仍独立执行。
  6. 会话切换不串上下文。旧消息表情需要保留明确引用对象。已知目标属于 /cd 前的旧会话时，首版建议提示该建议已失效，不把旧工作目录里的批准套用到新目录任务。

4. 新增、撤销与重复事件的语义

  • 新增表情：每个有效事件作为一条新用户消息排队，不限于 YES / NO；例如 [碰拳] 也按普通用户输入处理。
  • 撤销表情：首版不产生新模型请求，不自动取消或回滚此前任务。需要停止时仍使用 /stop。
  • 同一事件重投：只处理一次。保留 SDK 去重，再按原始 event_id 维护内部有界去重；需要跨重启防重时保存已受理事件标识，不能声称 SDK 内存去重可以跨重启。
  • 撤销后重新添加：属于新操作，应允许成为新请求，不按“消息 ID + 用户 + 表情”永久去重。
  • 短时间 YES 再 NO：作为两条输入按接收顺序排队；后者不是自动撤回前者。首版不加隐式防抖或自动撤销语义。

5. 建议实施与验收

先实现共享 EmojiText 转换器及当前/历史富文本解析，再增加 ReactionInput 适配层、独立输入身份和出站关联记录。复用 ChatService、ReplyContext 与既有协程生命周期，不新增独立线程调度器，不改后端运行协议。

测试重点：纯表情及图文混排；多个表情顺序；Yes/No 大小写；未知表情与 sticker；普通文本代码不误改；仅允许用户操作本机器人消息；Typing 不触发；added/removed 实际值；重复投递与撤销重加；多次回复同一目标；引用循环问题；消息查询失败；跨目录旧建议；表情与普通消息并发到达时 FIFO；/stop 取消待处理表情请求。

真实联调需覆盖私聊和群聊：对机器人消息点 Yes/No，确认收到新增事件、原消息引用正确、回复路由正确；同时确认移除表情不会触发新任务。运行测试与打包按项目约定执行；installDist 前必须先停止旧实例，不覆盖运行中 JAR。
