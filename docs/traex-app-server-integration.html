实现更新：配置选择与双后端

后端通过本机 ~/.agent-im-bridge-kt/config.json 的 backend 字段选择，仅接受 codex 或 traex，重启生效。旧配置缺失字段时使用 Codex，首次绑定显式保存默认值。不提供 --backend 或聊天切换命令。此处取代下方调研阶段的命令行选择建议。

"backend": "traex",
"sandboxMode": "read-only"

共享 AppServerAgentRunner 负责原生轮次和停止；BackendSpec 负责二进制、环境、resume 参数及诊断。保留 --codex-bin，增加 --traex-bin。仅启动选中后端，启动失败不自动切换。Traex 不发送 excludeTurns。

会话存储 v3 使用 backendId 与 runtimeRoot，兼容 v1/v2 的 Codex 绑定，下一次成功提交原子升级。后端各自保存会话和目录，切回恢复原绑定；/cd 切换不同目录继续清除目标旧绑定。

本机 0.204.1 已通过空闲轮次的独立 RPC 核对：代码 -32600 且精确诊断 no active turn to interrupt 才允许 Traex 重试，间隔 300 ms 起指数递增至 2 s，窗口不超过 30 s；其他错误不重试。终态结束重试，RPC 接受不释放槽位，未确认继续占槽。/status、帮助和错误显示当前后端。

新增双后端离线协议回归、配置及迁移测试；真实测试入口为 TRAEX_LIVE_TEST=1 ./gradlew test --tests top.ntutn.agent.bridge.TraexLiveTest。权限、FIFO、并发、关闭清理及日志保密约束保持不变。

结论与边界

Traex 支持独立 app-server --listen stdio://，具备与当前 Bridge 对应的 thread/start、thread/resume、turn/start、turn/interrupt 和 turn/completed 接口。应复用当前 AppServerClient 与原生执行句柄，通过后端配置适配 Traex，不退回 exec。

停止依据是匹配 thread ID、turn ID 的轮次终态，而不是中断 RPC 返回成功。一次本机测试证明这条控制链可用，不代表任意模型、工具、平台和版本都已完成验收。

长输入停止实测

探测启动了自己的 app-server，没有连接或停止桌面服务。请求约 64 KB（64,110 UTF-8 字节）的合成长文本，要求长篇分析、不使用工具；在 turn/start 尚未返回时记录停止意图。

相对时间事件含义
0.711 秒记录停止意图保留尚未返回的 turn/start RPC。
0.712 秒turn/start 返回 turn ID已有 ID 不代表轮次已完成内部激活。
0.712 秒首次 turn/interrupt 返回 -32600服务端诊断含 no active；停止尚未确认。
1.015 秒约 300 ms 后同 ID 重试，中断 RPC 成功仅代表中断被接受。
1.016 秒turn/completed → interrupted收到匹配轮次终态，停止确认；服务进程仍存活。
5.234 秒同会话下一轮 agentMessage，phase=final_answer返回预期 STOP-PROBE-OK。
5.469 秒下一轮 turn/completed → completed无需重启 app-server 即可继续工作。
5.512 秒thread/resume 返回同一 ID本次服务内恢复调用成功。

上述时间是本机单次观测，不是延迟承诺。另有两次前置探测：一次确认立即中断被拒绝；一次因探测客户端默认 64 KiB 行读取限制而失败。将读取上限调高后完成上述完整链路。失败探测均清理了自身进程。

实际使用的 RPC

traex app-server --listen stdio://

通过 stdio 逐行 JSON 匹配请求 ID。先 initialize，再发送 initialized 通知。

{"id":1,"method":"initialize","params":{"clientInfo":{"name":"agent_im_bridge_kt","version":"1.0"}}}
{"method":"initialized"}
{"id":2,"method":"thread/start","params":{"cwd":"/workspace","approvalPolicy":"never","sandbox":"read-only","ephemeral":false}}

取得 thread.id 后先等待 Bridge 会话落盘，再订阅事件并提交轮次。示例 ID 为占位值。

{"id":3,"method":"turn/start","params":{"threadId":"THREAD_ID","cwd":"/workspace","approvalPolicy":"never","sandboxPolicy":{"type":"readOnly"},"input":[{"type":"text","text":"用户正文"}]}}
{"id":4,"method":"turn/interrupt","params":{"threadId":"THREAD_ID","turnId":"TURN_ID"}}

终态核心字段如下（省略其他字段）：

{"method":"turn/completed","params":{"threadId":"THREAD_ID","turn":{"id":"TURN_ID","status":"interrupted"}}}

正常答案只取本轮 item/completed 中的 agentMessage，过滤 commentary。本次确认存在 phase=final_answer。schema 同时说明某些 provider 的 phase 可能为空，应沿用经过测试的兼容逻辑，不能把所有助手消息拼在一起。

最重要的适配：停止状态机

  1. 未提交 turn/start：停止后不再提交该轮，完成请求清理。
  2. turn/start 已在途：只记录 stopRequested，继续等待 RPC 结果；取得 turn ID 后对该 ID 中断，不能取消公共读取协程。
  3. 尚无活动轮次：保留停止意图；识别后端明确的激活竞态诊断，对同一 thread/turn 做有界退避重试，并同时监听终态。不要把所有 -32600 错误都当成可重试。
  4. 中断被接受：继续等待匹配的 turn/completed；RPC 接受不释放运行槽位。
  5. 轮次终态先到：结束中断重试。对“自然完成与停止相撞”的情况按 Bridge 已有停止语义返回，不触发模型重跑。
  6. 30 秒仍未确认：提示异常并持续占槽；重复 /stop 复用原停止过程，不能再次清除停止后新加入的队列。不得自动强杀或将其判为成功。
  7. 传输失效：结果不明且自身服务仍存活时维持占槽，不自动重跑。整个 Bridge 关闭时才请求原生中断、最多等待 5 秒，再清理自身进程树。

调研时 CodexRunner 的中断逻辑只发送一次 turn/interrupt；直接换成 Traex 二进制会漏掉此次实测的“尚无活动轮次”竞态。本次实现已补充精确识别及退避重试。重试策略属于实现建议，本次仅验证一次 300 ms 后的重试有效。

模块建议

协议差异与下一步验收

本机可通过 traex app-server generate-json-schema --out DIR 导出协议。已核对必要的 thread/turn 参数与中断终态。值得注意：Traex 的 ThreadResumeParams 未声明当前 Codex 代码传入的 excludeTurns，Traex 适配器应先省略该字段，不依赖未知字段被忽略。

  • 补齐“start 响应早于激活、立即停止”的假 RPC 回归；同时覆盖通知早于响应、自然完成竞态、重复停止、断连和迟到事件。
  • 真实验证持续生成途中中断、工具子进程执行途中中断，以及两个聊天并发时只停止指定轮次。本次验证的是长输入提交后的早期中断，不代表这些场景均已通过。
  • 验证 app-server 重启后的 resume、会话存储失败不会提交 turn/start，以及实际权限在新建和续聊中一致。
  • 检查超长 JSON 行和大型响应，避免 64 KiB 默认限制导致读循环退出；日志仍不输出完整载荷。
  • 中断 30 秒无终态的处理是停止确认异常机制，不是模型执行超时。测试中按终态断言，不按 RPC 接受断言。
  • 业务变更后运行 ./gradlew test；安装新版前先停止旧实例，再执行 installDist，不覆盖运行中的 JAR。
